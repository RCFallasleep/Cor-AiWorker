## 零、术语与部署形态

系统由三个程序组成。本文档中的「后端」一律指**本地服务**。

| 术语 | 是什么 | 运行在哪 | 代码目录 |
|---|---|---|---|
| **界面** | 浏览器页面或桌面应用窗口 | 用户电脑 | `web/`（M3） |
| **本地服务** | Python 进程：调用模型、执行工具、管理 MCP 子进程、读写 SQLite 与钥匙串 | 用户电脑，只监听 127.0.0.1 | `server/` |
| **中转服务器（Relay）** | 只转发加密上下文包，无业务逻辑，看不到明文 | 任意可公网访问的机器（开发期为作者笔记本） | `relay/`（M6） |

```
┌──────────── 用户 A 的电脑 ────────────┐                    ┌──── 用户 B 的电脑 ────┐
│ 界面 ──127.0.0.1──▶ 本地服务 ──▶ 模型 API │                    │ 本地服务 ◀── 界面      │
│                    │  SQLite / 钥匙串   │                    │    ▲                 │
│                    │  MCP 子进程        │                    │    │                 │
└────────────────────┼─────────────────┘                    └────┼─────────────────┘
                     │ 加密的上下文包     ┌──────────────┐          │
                     └─────────────────▶│    Relay     │──────────┘
                                        └──────────────┘
```

本地服务之所以不能省略（全部放进浏览器）：浏览器无法启动 MCP 子进程、无法访问系统钥匙串、无法读写本地文件，关闭页面后也无法继续运行。桌面安装包形态下，本地服务作为子进程随应用窗口启动，对用户不可见。

## 一、总体分层

```
┌──────────────────────────────────────────────────────────────┐
│ Web UI（M3）                                                  │
└──────────────────────┬───────────────────────────────────────┘
                       │ HTTP + SSE，仅 127.0.0.1
┌──────────────────────▼───────────────────────────────────────┐
│ API 层  api/          路由、请求校验、本地安全（Host 校验、令牌） │
├──────────────────────────────────────────────────────────────┤
│ 应用层  app/          运行管理、会话管理、审批、事件广播与持久化   │
├──────────────────────────────────────────────────────────────┤
│ 内核    kernel/       Agent 循环、模型适配器、工具、权限、上下文   │
│                      纯逻辑：不依赖 HTTP、不依赖数据库            │
├──────────────────────────────────────────────────────────────┤
│ 基础设施 storage/  keystore  config  MCP 子进程                 │
└──────────────────────────────────────────────────────────────┘
```

**依赖规则：只能向下依赖。** 内核不 import 存储与 API。内核通过接口（Protocol）声明它需要什么（例如「审批闸门」），由应用层注入实现。这样内核可以在没有数据库、没有网络的情况下被完整测试，也能被 CLI、Web、评测脚本复用。

## 三、一次运行的数据流

```
用户发送消息
   │
   ▼
RunManager 创建 Run（后台任务），加载会话历史（原生 JSON）
   │
   ▼
kernel.loop.run() ──────────────── 产出事件 ─────────────────┐
   │                                                        │
   │ ① 修复历史：上次中断留下的未回复工具调用 → 补「已取消」结果     │
   │ ② 追加用户消息                                            │
   │ ③ Provider.stream(system, history, tools)                │
   │      → ThinkingDelta / TextDelta …（流式）                │
   │      → TurnResult（文本、工具调用、Token、助手原生消息）       │
   │ ④ 对每个工具调用：                                         │
   │      参数校验 → 重复检测 → 权限决策                          │
   │        allow ──────────────┐                              │
   │        ask → 审批闸门（等待用户）─┤                           │
   │        deny → 错误结果       │                              │
   │      执行工具 ◄──────────────┘                              │
   │      结果来自外部 → 标记不可信，本次运行「已污染」              │
   │ ⑤ 工具结果追加到历史，回到 ③                                │
   │ ⑥ 无工具调用 / 截断 / 拒答 / 达到轮数上限 → 结束              │
   ▼                                                        ▼
                                    ┌───────────────────────────────┐
                                    │ 事件消费者                      │
                                    │  · SSE 推送给 UI（实时显示）     │
                                    │  · 写入 run_events（运行日志）   │
                                    │  · 写入 messages（会话历史）     │
                                    │  · 评测脚本（自动打分）          │
                                    └───────────────────────────────┘
```

## 四、关键设计

### 4.1 事件流：运行过程的唯一事实来源

循环不直接打印、不直接写库，而是**产出一串事件**。UI、运行日志、会话持久化、评测都是这串事件的消费者。好处：

- 一套逻辑，多种用途：同一次运行，UI 看到的、日志记录的、评测读取的完全一致
- 运行日志可以**回放**：按顺序重放事件即可还原整个过程
- 内核可测试：测试只需断言产出的事件序列

**实时推送与运行日志完全一致**：应用层为每个事件分配序号，推送给订阅者的和写入数据库的是同一条记录。流式片段逐条记录，但批量写入（攒满 64 条或 0.5 秒写一次），其余事件立即写入。运行期间全部事件保留在内存中供订阅；运行结束、数据写完后才移出内存，之后的订阅从数据库回放，保证不丢不重。

> 曾考虑把连续片段合并后再存，但合并需要缓冲，会让实时显示的内容与日志不一致，断线续传时出现重复或缺漏，因此放弃。

| 事件 | 含义 | 对外 / 内部 |
|---|---|---|
| `run_started` | 运行开始（模型、会话） | 对外 |
| `thinking_delta` / `text_delta` | 流式思考 / 正文片段 | 对外 |
| `tool_call` | 模型请求调用工具（含风险等级） | 对外 |
| `approval_requested` / `approval_resolved` | 等待审批 / 审批结果 | 对外 |
| `tool_result` | 工具执行结果 | 对外 |
| `turn_finished` | 一次模型调用结束（Token、结束原因） | 对外 |
| `run_finished` / `run_failed` | 运行结束 / 异常 | 对外 |
| `history_appended` | 有新的原生消息要写入会话历史 | 内部（只用于持久化，不推给 UI） |

### 4.2 无状态适配器 + 原生历史

- **适配器无状态**：只负责「原生格式的历史 → 调用模型 → 原生格式的新消息」。
- **会话历史以各协议的原生 JSON 保存**：Claude 的 thinking 块、DeepSeek 的 `reasoning_content` 原样保留，不转换成中间格式。
- **会话创建时绑定模型，不支持中途切换**：不同协议的历史互不兼容，转换必然丢信息。
- **发送前由适配器决定发什么**：例如 DeepSeek 只回传当前问题内的 `reasoning_content`，更早的在发送时剔除，存储里仍完整保留。
- **历史自愈**：运行被取消或进程崩溃时，历史里可能留下「有工具调用、没有结果」的助手消息，下次请求会被 API 拒绝。每次运行开始前，适配器检查并补上「已取消」结果。

```python
class Provider(Protocol):
    name: str
    model: str
    def user_message(self, text: str) -> NativeMessage: ...
    def tool_result_messages(self, results: list[ToolResult]) -> list[NativeMessage]: ...
    def unanswered_tool_calls(self, history: list[NativeMessage]) -> list[str]: ...
    def stream(self, system: str, history: list[NativeMessage],
               tools: list[ToolSpec]) -> AsyncIterator[ThinkingDelta | TextDelta | TurnResult]: ...
```

### 4.3 权限与审批

**风险等级**：`read`（只读本地信息）、`network`（访问外部网络）、`write`（修改本地文件或数据）、`execute`（执行命令或代码）。

**默认策略**（可按工具覆盖）：

| 风险 | 默认 | 本次运行已污染时 |
|---|---|---|
| read | 允许 | 允许 |
| network | 询问 | 询问 |
| write | 询问 | 询问（不可被覆盖为「允许」） |
| execute | 询问 | 询问（不可被覆盖为「允许」） |

**污染**：只要本次运行中有工具返回了外部内容（网页、搜索结果、收件箱），运行即标记为「已污染」。此后 write / execute 类调用即使用户设置了「总是允许」，也会强制询问。这是防提示词注入的核心机制：模型可能被外部内容操纵，但写入与执行必须经过人。

**审批闸门**是内核声明、应用层实现的接口：CLI 实现为终端输入；Web 实现为「挂起等待 → 用户在 UI 点击 → API 回调唤醒」。

### 4.4 工具与 MCP

- **命名空间**：MCP 工具注册为 `{服务名}__{工具名}`（如 `fetch__fetch`），避免不同服务重名，也让模型和用户看到来源。
- **不可信标记**：外部内容统一包裹为 `<untrusted source="…">…</untrusted>`，系统提示词说明其中的指令不得执行。
- **结果截断**：单次工具结果超过上限时截断并注明原长度，防止上下文被撑爆。
- **MCP 服务配置**存数据库（命令、参数、默认风险、启用状态）；其中的密钥类环境变量存钥匙串，配置里只保存引用。
- **启动参数受控**：例如 fetch 服务的 `--allow-private-ips` 会削弱 SSRF 防护，只能由用户在设置中显式开启。

### 4.5 上下文组装

系统提示词按「稳定 → 易变」分层拼装，以最大化提示缓存命中：

```
① 平台规则（安全规则、不可信内容处理）   ← 几乎不变
② Agent 人设（P2）                     ← 按会话固定
③ 长期记忆摘要（P1）                    ← 偶尔变化
④ 环境信息（今天的日期、操作系统）        ← 每天变化
```

工具定义列表按名称排序后再发送，保证字节级稳定（工具顺序变化会使缓存失效）。

### 4.6 存储

单个 SQLite 文件，放在系统应用数据目录（macOS：`~/Library/Application Support/cor-aiworker/`）。WAL 模式、`busy_timeout`、`foreign_keys` 在统一的连接工厂中设置。迁移使用 `PRAGMA user_version` + 顺序编号的 SQL 文件。

| 表 | 内容 |
|---|---|
| `sessions` | 会话：标题、Provider、模型、创建/更新时间 |
| `messages` | 会话历史：序号、原生 JSON |
| `runs` | 运行：所属会话、状态、开始/结束时间、Token 汇总 |
| `run_events` | 运行日志：序号、事件类型、事件 JSON |
| `mcp_servers` | MCP 服务配置 |
| `tool_policies` | 按工具覆盖的权限策略 |

API Key 不进数据库，只存在系统钥匙串。

### 4.7 本地服务安全模型

本地服务最大的威胁不是「外网的人」，而是**你浏览器里打开的任意网页**（v1 的 CORS `*` 就是这个问题）。

| 威胁 | 防护 |
|---|---|
| 局域网内其他设备访问 | 只监听 `127.0.0.1` |
| 任意网页跨域调用 `localhost` | CORS 只允许自身前端来源 |
| DNS 重绑定（恶意域名解析到 127.0.0.1 绕过同源策略） | 校验 `Host` 头必须是 `127.0.0.1:端口` 或 `localhost:端口` |
| 本机其他程序或网页伪造请求 | 每次启动生成随机令牌，前端由同源页面注入，所有 API 请求必须携带 |

**令牌的获取**：本地服务启动后把端口与令牌写入数据目录下的 `server.json`（权限 600，仅当前用户可读），退出时删除。本机工具（命令行、桌面外壳）从这里读取；网页界面（M3）由本地服务托管页面时注入。浏览器原生的 `EventSource` 无法携带请求头，界面需用基于 `fetch` 的 SSE 读取方式。

**其他细节**：令牌比较使用常数时间算法；参数校验失败的响应不回显提交内容（可能是 API Key）；`/api/health` 与接口文档不需要令牌，但同样受 Host 校验保护。

### 4.8 可靠性

- **超时**：连接超时与总超时由 SDK 配置；流式输出另设**空闲超时**（连续 N 秒没有新数据即判定卡死），解决 v1「流中途卡住会永远挂着」的问题。
- **重试**：交给官方 SDK 的内置重试（429、5xx、连接错误），业务层不重复实现。
- **取消**：运行是后台任务，用户可显式取消；取消后通过「历史自愈」保持会话可继续。
- **运行与连接解耦**：浏览器断开不会中止运行（运行可能正在等待审批）。重新连接后按事件序号补发错过的事件。
- **单实例**：同一数据目录同时只允许一个进程（ADR-009）。
- **MCP 子进程输出隔离**：子进程的 stderr 写入 `logs/mcp-{服务名}.log`，不混入本地服务输出。

### 4.9 HTTP API

所有接口位于 `/api` 下，除 `/api/health` 外均需 `Authorization: Bearer <令牌>`。错误统一为 `{"error": {"code", "message"}}`，`code` 供界面判断。

| 方法与路径 | 作用 |
|---|---|
| `GET /api/providers` · `PUT/DELETE /api/providers/{name}/key` | 模型提供方列表（只返回「是否已配置 Key」）；设置或删除 Key |
| `POST/GET /api/sessions` · `GET/PATCH/DELETE /api/sessions/{id}` | 会话增删改查；详情含正在进行的运行 |
| `POST /api/sessions/{id}/runs` | 发消息，立即返回 `run_id`（202）；首条消息自动成为会话标题 |
| `GET /api/sessions/{id}/runs` · `GET /api/runs/{id}` | 运行列表与详情（状态、Token 汇总） |
| `GET /api/runs/{id}/events` | SSE 事件流；`Last-Event-ID` 头或 `after` 参数用于续传 |
| `POST /api/runs/{id}/approvals/{approval_id}` | 答复审批 `{"approved": bool}` |
| `POST /api/runs/{id}/cancel` | 取消运行 |
| `GET /api/tools` · `PUT/DELETE /api/tools/{name}/policy` | 工具列表（风险、是否不可信、覆盖策略）；设置或清除策略 |

完整定义见运行中服务的 `/api/docs`。

### 4.10 界面主题与皮肤（M3）

界面外观是两个独立维度的组合，都设置在页面根元素上：

| 维度 | 取值 | 属性 |
|---|---|---|
| 明暗模式 | 跟随系统 / 浅色 / 深色 | `data-theme` |
| 皮肤 | 品牌蓝（默认）/ 其他皮肤 | `data-skin` |

- **组件只引用颜色变量，不写颜色值**。v1 的组件里有 400 多处硬编码颜色，这是它无法换皮肤的根源。CI 中加入检查：组件代码里出现颜色字面量即失败。
- **皮肤 = 一组变量取值**（浅色、深色各一套）。新增皮肤只需增加一份配置，不改任何组件。
- **皮肤配置可扩展**：当前只包含颜色；格式上预留背景、图标、动效等字段，对应 PRD 中 P2 的「界面个性化」。动效必须尊重系统的「减少动态效果」设置。
- **预留自定义皮肤导入**：以 JSON 描述变量取值，导入时只接受合法的颜色值，防止借皮肤注入任意 CSS。
- **偏好保存在本地服务的设置中**，浏览器与桌面窗口保持一致；页面在首次渲染前读取，避免先闪一下默认样式。
- **logo** 沿用 v1 作者设计的 `logo.svg`（递归三层三角形），颜色改为 `currentColor`，随皮肤的强调色变化；默认皮肤「品牌蓝」的取值来自 logo。

| 内核单元测试 | 伪造 Provider 按脚本返回结果，断言事件序列 | 否 |

## 七、架构决策记录（ADR）

### ADR-001 按协议自建模型适配器，不引入 LiteLLM
- **背景**：需要同时支持国内外模型。
- **决定**：Anthropic 原生协议与 OpenAI 兼容协议各一个适配器，分别使用各家官方 SDK。
- **理由**：两个协议即可覆盖目标模型；经 OpenAI 格式转换会丢失 Claude 的 thinking 回传、effort、拒答回退等能力。（Spike 01 实测）
- **代价**：新增一种协议时需要写一个新适配器（约 150 行）。

### ADR-002 会话历史保存原生格式，会话绑定模型
- **背景**：各家推理内容（thinking 块、reasoning_content）必须原样回传。
- **决定**：历史以原生 JSON 保存；会话创建时绑定 Provider 与模型。
- **代价**：不能在同一会话中途换模型；换模型需新建会话（未来可提供「带摘要新建」）。

### ADR-003 事件流作为运行过程的唯一事实来源
- **决定**：循环只产出事件；UI、日志、持久化、评测都是消费者。
- **理由**：多个用途共享同一份数据，运行日志天然可回放，内核易测试。
- **代价**：事件类型需要版本管理，改字段要考虑旧日志的兼容。

### ADR-004 运行与连接解耦
- **决定**：运行是后台任务，不随浏览器断开而中止；显式取消；按事件序号支持断线续传。
- **理由**：运行可能长时间等待审批；网络抖动不应丢失工作。
- **代价**：需要管理后台任务生命周期，进程退出时要妥善收尾。

### ADR-005 污染标记驱动的审批升级
- **决定**：运行中出现外部内容后，write / execute 类调用强制审批，不受「总是允许」影响。
- **理由**：不依赖模型自觉防注入（Spike 01 中模型识别了直白注入，但不能作为安全保证）。
- **代价**：浏览网页后的写操作会多一次确认。
- **残余风险**：network 类工具默认是「询问」；若用户把某个联网工具设为「总是允许」，被注入的模型仍可能借它把数据外传（Spike 01 的注入样本正是这种手法）。这是有意的取舍：强制每次联网都询问会让多步检索几乎不可用。设置界面需对「总是允许联网工具」给出明确提示。

### ADR-006 单文件 SQLite + `user_version` 迁移
- **理由**：本地单用户，零运维，便于打包进桌面应用。
- **代价**：不适合多进程并发写；平台本就是单进程。

### ADR-007 密钥只存系统钥匙串
- **决定**：API Key 与 MCP 服务的密钥类环境变量只存系统钥匙串；不进数据库、日志、前端存储。
- **代价**：无图形界面的 Linux 服务器需要额外的钥匙串后端；可降级为加密文件（后续再定）。

### ADR-008 本地服务四层防护
- **决定**：127.0.0.1 监听 + 严格 CORS + Host 头校验 + 启动令牌。
- **理由**：v1 的主要漏洞来自「本地服务对浏览器网页不设防」。
- **代价**：前端需要获取并携带令牌，开发时稍麻烦。

### ADR-009 同一数据目录单进程
- **背景**：进行中的运行与审批等待只存在于进程内存；两个进程共用数据库时，后启动者的崩溃恢复会把前者正在进行的运行误标为已取消。
- **决定**：本地服务启动时对数据目录加排他文件锁（POSIX `flock` / Windows `msvcrt.locking`），第二个进程直接报错退出。
- **代价**：`serve` 运行时不能同时用 `chat`；命令行的 `mcp`、`key` 子命令不经过运行管理，不受此限制。
