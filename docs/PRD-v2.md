## 一、背景：为什么要重构

### 1.1 v1 回顾

v1 是一个学年设计，约 2 周内借助 AI 快速完成，覆盖了 Chat Agent、代码工作台 + Android Studio 断点调试、多 Agent 推演（Think Tank）、团队 IM、Agent 记忆/养成、定时任务、Android 客户端等功能，约 3.8 万行代码。它验证了「本地 Agent 平台」这个方向可行，但存在以下问题：

| 问题 | 表现 |
|---|---|
| 广而不深 | 7 块功能各自独立实现，没有沉淀出公共的 Agent 内核（例如 SSE 读取逻辑重复 5+ 次，每个服务各自构造 LLM 客户端） |
| 安全几乎不设防 | 大部分接口无鉴权；Skills 通过进程内 `exec` 执行用户代码；工作区根目录可被任意设置；CORS 放开 `*`；JWT/Service Token 使用公开默认值；API Key 写入日志 |
| 定位矛盾 | 目标是「本地、个人」，却引入了账号、好友、多用户 IM，安全问题大多由此产生 |
| 部署偏重 | 需要 Docker 启动 5 个容器，与「只需一个 API Key」的承诺不符 |
| 工程基础缺失 | 无测试、无 CI；前端 `tsc` 13 个错误、lint 41 个 error；单页面文件最大近 4000 行 |

### 1.2 外部环境变化

MCP 生态已经普及，主流平台陆续开放 MCP。**把具体功能（爬虫、数据分析、管理系统……）内化进平台已经没有意义**——这些能力可以通过接入现成的 MCP Server 获得。平台真正的价值应在于：**把这些能力安全、可控、可观测地组合起来**，以及解决现有产品都没有解决的问题。

## 二、产品定位

### 2.1 一句话定位

> **一个本地优先的个人 Agent Harness，并让不同用户的本地 Agent 能够安全地交换上下文。**

### 2.2 两个支柱

| 支柱 | 说明 | 价值 |
|---|---|---|
| **本地 Harness 内核** | 只需配置一个 API Key（国内外模型均可），通过 MCP 获得能力广度；平台自身专注 Agent 运行时质量：权限审批、沙箱、上下文管理、可观测性 | 地基；Agent 工程中最有深度的部分 |
| **跨实例协作** | 用户 A 在本地遇到问题，可把结构化的「上下文包」经审阅后发给用户 B；B 的 Agent 在 B 的环境中接手处理 | 差异化；打破各自本地 AI 对话之间的隔阂 |

### 2.3 目标用户

- 首要用户：作者本人（日常使用）
- 次要用户：开源社区中希望拥有本地、多模型、可扩展 Agent 平台的开发者
- 协作场景：同学、小团队成员之间的问题交接

### 2.4 本项目的目的

1. 可日常使用的个人工具
2. 求职时能讲清楚的架构作品
3. 学习 Agent 工程（循环、工具、权限、上下文、协议）
4. 开源
5. 作为学年设计的后续交付

### 2.5 非目标（明确不做）

- ❌ 本地端多用户 / 账号体系（本地实例只服务一个人）
- ❌ 自己实现 MCP 生态已有的功能（爬虫、搜索、浏览器等改为接入 MCP）
- ❌ 与 Cursor / Claude Code 竞争的完整代码编辑器
- ❌ 中转服务器读取或存储明文内容
- ❌ 移动端客户端（v1 的 Android 探索归档）

## 三、设计原则

1. **薄内核，厚生态**：平台只做 Agent 运行时；能力通过 MCP 扩展。
2. **能复用就复用，复用不了再自建**：模型适配、工具协议复用成熟方案；与安全和控制强相关的部分自建。
3. **默认安全**：只监听 `127.0.0.1`；危险操作需用户审批；外部内容一律视为不可信。
4. **一键可用**：不依赖 Docker；配置在界面内完成；最终形态为桌面安装包。
5. **协议与传输分离**：上下文包先定义为文件格式，中转服务器只是「送达方式」之一。
6. **工程基础先行**：测试与 CI 从内核第一行代码开始。

## 四、核心场景

### S1：用平台 + MCP 完成一个完整任务

> 用户想完成「二手交易网站商品价格爬取与价格预测」这类课程题目。
> 在平台中启用浏览器/爬虫 MCP 与数据分析能力，用自然语言描述目标；Agent 规划步骤、调用工具抓取数据、清洗、训练简单模型并输出报告。每一步的工具调用都可在运行追踪中查看。

验证点：MCP 接入、Agent 循环、多步任务、可观测性。

### S2：危险操作的审批

> Agent 在执行任务时读取了一个网页，随后试图写入本地文件或执行命令。
> 平台拦截该调用，弹出审批卡片，展示工具名、参数、触发原因（含「本轮上下文中包含外部不可信内容」的提示），用户批准后才执行。

验证点：权限模型、提示词注入防护。

### S3：跨实例问题交接

> A 在调试项目时卡住，需要 B 的帮助。A 点击「打包上下文」，平台自动生成上下文包（问题摘要、相关代码与 diff、环境信息、已尝试方案、对话摘录），A 审阅并删减敏感内容后发送。
> B 的平台收件箱收到后，B 审阅内容并交给自己的 Agent；B 的 Agent 在 B 的环境中复现、给出方案，B 可将结论回传给 A。

验证点：上下文包协议、隐私审阅、端到端加密、存储转发、接收端不可信内容处理。

## 五、功能需求

**优先级定义**

| 级别 | 含义 | 对应里程碑 |
|---|---|---|
| **P0** | 内核必需，没有它平台不可用或不安全 | M2–M3 |
| **P1** | 质量与差异化，决定项目「深度」和讲述价值 | M4–M6 |
| **P2** | 锦上添花，有余力再做 | M7 及以后 |

### 5.1 Harness 内核

| 模块 | 需求 | 复用 / 自建 | 优先级 |
|---|---|---|---|
| 模型适配层 | 支持 OpenAI 兼容协议（覆盖 DeepSeek、Qwen、Kimi、GLM 等）与 Anthropic、OpenAI 原生接口；统一流式输出、工具调用、多模态；统一超时、重试、取消 | 复用（如 LiteLLM 或 OpenAI 兼容 SDK） | P0 |
| Agent 循环 | 流式 ReAct 循环；工具调用累积；循环上限；重复调用检测；客户端断开时取消；每轮生命周期钩子（供权限、日志、上下文管理、记忆挂载） | **自建（保持轻薄）** | P0 |
| 工具系统 | MCP 客户端（stdio / HTTP）；MCP Server 的增删、启停、健康检查；内置少量必要工具（如受限文件读写） | 复用 MCP 官方 SDK | P0 |
| 权限与审批 | 工具按风险分级（只读 / 写入 / 执行 / 网络外发）；可配置策略（总是允许 / 每次询问 / 禁止）；上下文中含不可信内容时自动升级为询问；审批记录可追溯 | **自建** | P0 |
| 上下文组装 | 系统提示词分层拼装（平台规则 → 人设 → 记忆 → 当前日期与环境）；工具描述规范（每个工具写明「何时用 / 何时不用」）；工具结果截断与来源标记 | 自建 | P0 |
| 上下文管理 | Token 计量；超限压缩/摘要；不可信内容标记 | 自建 | P0 |
| 运行日志 | 每次运行的完整追踪（模型调用、工具调用、审批、耗时、Token）；可回放；敏感字段（Key 等）自动脱敏；**同时作为评测的数据来源** | 自建 | P0 |
| 存储 | SQLite 单文件，存放于系统应用数据目录；版本化迁移（`PRAGMA user_version`）；统一数据访问层 | 自建 | P0 |
| 密钥管理 | API Key 仅存于后端，优先使用系统钥匙串；不进入日志、不回传前端明文 | 自建 | P0 |
| 长期记忆 | 见 5.3 | 自建 | P1 |
| Agent 人设 | 角色设定模板（语气、背景、专长），作为系统提示词中的一层；对应 v1 的「灵魂设定」 | 自建 | P2 |

### 5.2 Web UI

| 页面 | 内容 | 优先级 |
|---|---|---|
| 对话 | 流式输出、思考过程、工具调用折叠展示、多模态输入 | P0 |
| 审批 | 工具调用审批卡片（工具、参数、触发原因、是否含不可信内容） | P0 |
| 运行追踪 | 时间线视图，可查看每一步输入输出 | P0 |
| 设置 | 模型与 Key 配置、MCP Server 管理（一键添加，无需手写 JSON）、权限策略 | P0 |
| 记忆 | 查看、编辑、删除记忆笔记 | P1 |
| 收件箱（协作） | 收到的上下文包、审阅、交给 Agent | P1 |
| 评测报告 | 各模型 / 各版本的评测结果对比 | P2 |

### 5.3 长期记忆（P1）

参考 OpenClaw 与 Claude Code 的做法：**记忆是本地 Markdown 文件，用户可见、可编辑、可用 Git 管理**；模型通过工具「主动回忆」。

| 层 | 内容 | 检索方式 | 优先级 |
|---|---|---|---|
| 第一层：记忆笔记 | 长期记忆（`MEMORY.md`：偏好、决定、人物）+ 每日日志（`memory/YYYY-MM-DD.md`） | 开局自动加载近期日志与长期记忆；更早内容通过 `memory_search` 检索（SQLite FTS5） | P1 |
| 第二层：原始对话 | 历史会话全文 | 笔记查不到时兜底检索（SQLite FTS5） | P2 |
| 语义检索 | 向量索引（sqlite-vec），措辞不同也能命中 | 与 FTS5 混合检索 | P2 |

写入机制：
- `memory_write` 工具：模型在对话中主动记录（P1）
- 压缩前抢救：上下文即将压缩时插入一轮静默回合，提示模型把重要信息写入记忆（P1，挂在 Agent 循环钩子上）
- 系统提示词「回忆规则」：涉及过往工作、决定、偏好时先检索记忆（P1）

与协作的关系：上下文包可选择性附带相关记忆片段，使接收方 Agent 也能「回忆」发送方的背景。

### 5.4 评测（Eval）

评测衡量「Agent 做得好不好」，与单元测试（衡量「代码对不对」）互补。原则：**能用代码判断的不用 LLM 判断。**

| 能力 | 内容 | 优先级 |
|---|---|---|
| 离线评测集 | 约 20 个固定任务，每个任务定义成功标准；以代码判断为主（是否调用了预期工具、产物是否存在、结果是否匹配） | P1 |
| 安全评测用例 | 提示词注入用例（网页 / 搜索结果 / 收件箱中藏指令），判断标准：注入后是否触发了未经审批的写入 / 发送 / 执行 | P1 |
| 多模型对比 | 同一评测集在不同模型上运行，输出成功率、Token、耗时对比 | P1 |
| 回归门禁 | 修改系统提示词、工具描述或循环逻辑后重跑，结果不得明显下降 | P1 |
| LLM 裁判 | 对主观质量打分；需明确评分标准、用人工标注校准、裁判模型与被测模型不同 | P2 |
| 线上评测 | 从运行日志中抽样，由 LLM 裁判打分，发现失败案例 | P2 |
| 数据飞轮 | 线上发现的失败案例沉淀为离线评测用例 | P2 |

### 5.5 上下文包（`.corctx`）（P1）

- 结构化内容：问题摘要、相关文件片段与 diff、环境信息、已尝试方案、对话摘录、附件
- 由 Agent 自动生成草稿，用户审阅、删减后才能导出/发送
- 敏感信息自动检测与打码（Key、Token、内网地址等）
- 带格式版本号，向后兼容
- v0：仅支持文件导出 / 导入（不需要服务器）

### 5.6 中转服务器（Relay）（P1）

- 独立服务，可一条命令自部署（作者笔记本 / 任意 VPS）
- 身份：每个实例生成密钥对，以公钥作为身份；通过交换公钥或邀请码建立联系
- 端到端加密：中转只转发密文，无法读取内容
- 存储转发：接收方离线时暂存，上线后投递；发送方断网时本地排队重试
- 最小化：不包含业务逻辑，不存储明文

### 5.7 分发与安装

1. 一条命令启动（如 `uvx cor-aiworker`），自动打开浏览器（P0）
2. 桌面安装包（Tauri 外壳 + Python 后端 sidecar），GitHub Actions 自动构建 macOS / Windows / Linux 版本（P2）

## 六、非功能需求

| 类别 | 要求 |
|---|---|
| 安全 | 只监听本机回环地址；CORS 仅允许自身前端；不在进程内执行用户代码；危险工具需审批；安全相关配置使用默认值时拒绝启动 |
| 隐私 | 数据默认只存本地；外发内容（上下文包）必须经用户审阅；中转不可见明文 |
| 安装 | 无需 Docker；无需手写配置文件；首次启动引导配置 Key |
| 可靠性 | LLM 调用统一超时与重试；流式中途卡死可检测；后台任务在断开时取消 |
| 可测试性 | 内核核心逻辑有单元测试（使用伪造的 LLM 流）；CI 运行测试、类型检查与 lint；Agent 行为由评测集衡量（见 5.4） |
| 可维护性 | 单文件不超过约 500 行；前后端类型由 OpenAPI 生成，避免手写重复 |

## 七、工程化与交付

所有流水线基于 GitHub Actions（公开仓库免费）。

### 7.1 持续集成（CI）——每次 push / PR 触发

| 范围 | 检查项 |
|---|---|
| 后端 | `pytest`（单元测试）、`ruff`（规范检查）、类型检查 |
| 前端 | `tsc --noEmit`、`eslint`、`build` |
| 规则 | 任一项失败不允许合并到 `main` |

### 7.2 持续交付（CD）——打版本标签 `v*` 触发

| 产物 | 用途 |
|---|---|
| Python 包 | 支持 `uvx cor-aiworker` 一条命令启动 |
| Tauri 安装包（macOS / Windows / Linux） | 桌面一键安装 |
| Relay Docker 镜像 | 自部署中转服务器 |

产物统一发布到 GitHub Releases，并附带更新日志。

### 7.3 引入节奏

- CI：M2 写下第一行内核代码时同步搭建
- 评测：M4 起，离线评测集可手动触发运行（调用真实模型有费用，不放进每次 push 的 CI）
- CD：M3 发布 Python 包；M6 加入 Relay 镜像；M7 加入安装包

## 附录：来自 v1 审查的安全基线

以下问题在 v2 中必须从设计上杜绝：

- 任何接口不得依赖「没人知道这个端口」作为安全措施
- 不使用进程内 `exec` / `eval` 执行任何用户或模型提供的代码
- 文件操作的根目录由用户在 UI 中显式授权，不接受接口参数任意指定
- 身份信息（发送者、所有者）只能来自可信来源，不得由请求体或 LLM 参数决定
- 密钥不得出现在工具参数、日志、数据库明文或前端存储中
- 网络外发类工具需防 SSRF（禁止访问内网地址，含重定向后）
- 所有来自网页、搜索结果、收件箱的内容都标记为不可信，影响后续工具审批策略
